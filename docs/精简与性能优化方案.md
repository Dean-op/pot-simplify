### 实施中相对本方案的三处偏离

**① `tauri.conf.json` 的 `deb`/`rpm` depends 里的 `tesseract-ocr` 保留了。** 原方案 C2 第 7 条说要删，那是我判断错了——它不是给 tesseract.js 用的，而是 Linux 平台「系统 OCR」的实现（`system_ocr.rs:107` 起用 `Command::new("tesseract")` 调命令行）。删掉会让 Linux 版的系统 OCR 失效，所以留着。

**② `flag-icons` 改成 emoji 国旗的方案不可行，最后是直接去掉国旗。** P2 里提到可以用 `🇨🇳` 替代整包 CSS，但 Windows 没有旗帜 emoji 字体，regional indicator 会退化成 `CN` 两个字母。所以语言选择器只保留语言名称文字，同时删掉 `utils/language.ts` 的 `LanguageFlag` enum，`flag-icons` 依赖照样卸掉了。

**③ 删 HTTP 服务时补了一个功能回归。** 识别窗口的「翻译」按钮原本是 POST 到本地 `60828/translate` 触发翻译的，删掉 server.rs 会让它失效。改成把 `window.rs::text_translate` 标记为 `#[tauri::command(async)]` 并注册进 handler，前端直接 `invoke('text_translate', { text })`，少一次本地 HTTP 往返。

### 相对方案的两处偏离

**① P1 里的 `manualChunks` 没做。** 方案说要把 `react`/`react-dom`、`@nextui-org`、
`services/translate`、`services/recognize` 各切一个 chunk。实测发现四个窗口都会静态
引用 react 和 NextUI，`services/*` 也分别只有一个窗口用 —— 拆出来只是多几个文件请求，
任何一个窗口的实际下载量都不会变少。所以只做了 lazy 拆窗口。

**② P6 走的是「中期」方案，跳过了「短期」的 prop 传递。** 模块级注册表的收益覆盖全应用，
而 prop-drilling 只解决 `TargetArea` 一处，做了还要再推翻一次。注册表实现里
`syncToStore` 的 debounce 保持 per-instance（方案里提醒过的坑），另外顺手合并了同一个 key
的并发首读：4 个 `TargetArea` 同时挂载时 `store.get` 从 40 次降到 10 次。

### 追加：lingua 语种裁剪到中日英（`8d36728`）

Dean 确认常用语言只有中日英，所以三处一起改了：`Cargo.toml` 的 features、`LANGUAGES` 数组、`match` 分支。`Cargo.lock` 少掉 19 个 `lingua-*-language-model` 包（719 → 700），没有任何 crate 升版本。

模型是嵌进二进制的数据，22 个语种的 `.br` 合计 20.12 MB，留下的三个只有 1.18 MB：

| 语种 | 模型体积 |
| --- | --- |
| english | 1.13 MB |
| chinese | 0.03 MB |
| japanese | 0.02 MB |
| 其余 19 个（已删） | 18.94 MB |

用一个最小 crate 套同一份 `[profile.release]` 实测（Linux 目标）：22 语种 82.97 MB，3 语种 6.11 MB，差 **76.9 MB**，全部落在 `.rodata`。两边都符合「嵌入体积 ≈ 4.25 × `.br` 体积」，线性关系很干净。不过 Windows MSVC 的链接器会做 identical COMDAT folding，实际省多少要等你 `cargo build --release` 之后才算准 —— **下限是那 18.9 MB 的模型数据**。

行为也逐条验证过：

| 输入 | 结果 |
| --- | --- |
| 中 / 日 / 英 | 全部判对，短文本也对（`翻译` → zh_cn、`hello` → en） |
| 俄 / 韩 / 阿拉伯 / 泰 等非拉丁文字 | 字符集对不上任何语种，`detect_language_of` 返回 `None`，落到兜底的 `en` |
| 法 / 德 / 越 等拉丁语系 | 判成英语 |

影响面有限：本地引擎不是默认（默认是百度），检测结果只用在三处 —— 界面上那个语言标签、译文语言与检测语言相同时自动切第二目标语言、系统 OCR 判断是否中文好去掉空格。发给翻译服务的 `sourceLanguage` 始终是 `auto`，检测错了不会把源语言标错。

> 韩语模型只有 0.01 MB，想加回来几乎不花体积（`Cargo.toml` features、`LANGUAGES`、`match` 三处各加一行）。

## 二、动手前必须先处理行尾

`git status` 显示 282 个文件 modified，`git diff --stat` 是 56887 增 / 56887 删——增删完全相等，说明这不是真实改动，而是工作区 CRLF 与索引 LF 的差异。

不先处理，后面每个 commit 的 diff 都会被 5.6 万行噪音淹没，也没法用 diff 复查「删对了没有」。做法是在仓库根加 `.gitattributes`：

```gitattributes
* text=auto eol=lf
*.png binary
*.ico binary
*.icns binary
*.wasm binary
*.woff2 binary
```

然后 `git add --renormalize .`，单独提交。这一步做完 `git status` 应该是干净的。在此之前任何提交都必须 `git add <具体文件>`，**绝不能** `git add .` 或 `git commit -a`。

## 三、三家 provider 怎么接

### 3.1 组织方式：一套通用服务 + 提供商预设

pot 的服务实例键是 `服务名@随机ID`（`src/utils/service_instance.ts`），同一个服务可以添加任意多个实例，每个实例有独立的配置和自定义显示名。这正好覆盖你的需求，不需要为三家各写一份代码：

- **翻译**：直接用现有的 `openai` 服务，给它的 Config 加一个提供商预设下拉，选中后自动填 `requestPath`
- **识别**：新建一个 `llm` 服务（视觉 OCR），同样带提供商预设下拉

配好之后你的服务列表大致是这样，每个实例各自配 `model`，翻译和识别天然用不同模型：

| 实例名（自己改） | 服务 | requestPath | model 举例 |
| --- | --- | --- | --- |
| 百炼-翻译 | `openai@a1` | `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` | `qwen-plus` |
| 硅基-翻译 | `openai@b2` | `https://api.siliconflow.cn/v1/chat/completions` | 按当前可用模型填 |
| 百炼-识别 | `llm@c3` | 同上 | `qwen-vl-plus` 类视觉模型 |
| 硅基-识别 | `llm@d4` | 同上 | 硅基的视觉模型 |
| 自建/中转 | `openai@e5` / `llm@f6` | 任意 OpenAI 兼容地址 | 任意 |

三家的预设值（已核实，都是 OpenAI 兼容的 `/chat/completions`）：

| 提供商 | Base URL | 鉴权 | 模型列表接口 |
| --- | --- | --- | --- |
| 阿里百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `Authorization: Bearer <API-KEY>` | `GET {base}/models` |
| 硅基流动 | `https://api.siliconflow.cn/v1` | 同上 | `GET {base}/models` |
| 自定义 | 手填 | 同上 | 同上（若端点支持） |

**model 用可编辑输入框，不做硬编码下拉。** 两家的模型目录变动很快（我的知识截止到 2025 年 5 月，现在报出来的型号名很可能已经过期或有更好的），写死只会误导。方案是：输入框 + 旁边一个「拉取模型列表」按钮，点一下 `GET {base}/models` 把返回的 id 填进下拉候选，拉不到就退回纯手填。

### 3.3 识别侧：新建 `src/services/recognize/llm/`

上游**没有任何基于视觉模型的 OCR 服务**，这部分是纯新增。三个文件：

**`info.ts`** —— 注意 recognize 服务的 `Language` enum 语义和 translate 不同：translate 映射成英文语言名喂给 prompt，recognize 一般映射成服务自己的语种代码。这里我们要塞进 prompt，所以按 translate 的风格映射成英文名：

```ts
export const info = { name: 'llm', icon: 'logo/openai.svg' };
export enum Language {
    auto = 'Auto',
    zh_cn = 'Simplified Chinese',
    zh_tw = 'Traditional Chinese',
    en = 'English',
    ja = 'Japanese',
    ko = 'Korean',
    // ...与 translate/openai/info.ts 保持同一份语种表
}
```

**`index.jsx`** —— 契约是 `recognize(base64, lang, options)`。已核实 `src-tauri/src/cmd.rs:53-74` 的 `get_base64()` 返回的是 `pot_screenshot_cut.png` 的**裸 base64，不带 `data:` 前缀**，所以要自己拼 data URL：

```jsx
import { fetch, Body } from '@tauri-apps/api/http';
import { Language } from './info';

export async function recognize(base64, lang, options = {}) {
    const { config } = options;
    const { requestPath, model, apiKey, prompt, requestArguments } = config;
    const apiUrl = buildChatCompletionsUrl(requestPath);   // 与 3.2 的补全逻辑共用

    const res = await fetch(apiUrl.href, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${apiKey}` },
        body: Body.json({
            model,
            messages: [{
                role: 'user',
                content: [
                    { type: 'text', text: prompt.replaceAll('$lang', Language[lang]) },
                    { type: 'image_url', image_url: { url: `data:image/png;base64,${base64}` } },
                ],
            }],
            ...JSON.parse(requestArguments ?? '{"temperature":0}'),
        }),
    });
    if (!res.ok) throw `Http Request Error\nHttp Status: ${res.status}\n${JSON.stringify(res.data)}`;
    const text = res.data?.choices?.[0]?.message?.content;
    if (typeof text !== 'string') throw JSON.stringify(res.data);
    return text.replace(/^```[a-z]*\n?|```$/g, '').trim();   // 去掉模型爱加的代码围栏
}
export * from './Config';
export * from './info';
```

默认 prompt（可在配置里改）：

```
Extract all text from the image. Output only the extracted text, preserving the original line breaks. Do not add explanations, do not wrap the result in markdown code fences. If the image contains no text, output nothing.
```

`$lang` 占位符在选了具体语种时补一句 `The text is in $lang.`，选 auto 时不注入——写在 Config 的默认 prompt 里，用户可自行调整。

**`Config.jsx`** —— 抄 `src/services/recognize/tencent/Config.jsx` 的骨架（实例名输入框 + 帮助按钮 + 字段 + 提交即测试），字段换成：提供商预设下拉、`requestPath`、`apiKey`、`model` + 拉取模型列表按钮、`prompt` 用 `Textarea`、`requestArguments` 用 `Textarea`。

> 注意 pot 的 Config 表单「保存」等于「先跑一次真实请求，成功才保存」。tencent 的模板里硬编码了一张 59×30 的测试图 base64，直接沿用即可——视觉模型对它返回什么都无所谓，只要 HTTP 请求成功就算通过。

**接入登记**（漏一处就不生效）：

1. `src/services/recognize/index.jsx` 加 `import * as _llm from './llm';` + `export const llm = _llm;`
2. `src-tauri/src/config.rs` 的 `builtin_recognize_list` 加 `"llm"`
3. `src/i18n/locales/*.json` 加 `services.recognize.llm.*` 键（至少 `title`、各字段标签、`provider_preset`）

### 3.4 图片体积这一项要注意

百炼和硅基流动对上传图片都有大小与像素上限（百炼侧单图 10 MB 级别，像素也有上限）。4K 屏幕上框一大块区域，PNG 很容易上兆。`cmd.rs` 现在是原图直传，没有任何压缩。

## 五、性能优化阶段

> P1~P8 已全部实施完毕，实测数据和两处偏离说明见开头的「第二阶段」小节。下面保留的是当初的分析和做法，作为改动理由的记录。

前面 12 个 commit 主要是删，这部分是改，风险更高，一项一验。按投入产出排序：

### P1 拆分构建产物（收益最大）

**问题**：`src/App.jsx` 顶部静态 import 全部窗口组件，Vite 打出一个大 bundle。结果是弹出一个 350×420 的划词小窗，也要解析整个 Config 页面（含所有服务的 `Config.jsx`）。这是划词响应慢的主因。

**做法**：`windowMap` 改成 `React.lazy(() => import(...))` + `<Suspense fallback={<div />}>`，让 Vite 自然按窗口切 chunk；再在 `vite.config.js` 加 `build.rollupOptions.output.manualChunks`，把 `react`/`react-dom`、`@nextui-org`、`services/translate`、`services/recognize` 分别独立成 chunk。translate 窗口不该加载 `services/recognize`。

**风险**：低。窗口切换本来就是整页替换。

### P2 i18n 按需加载

**问题**：`src/i18n/index.jsx` 把 19 个 JSON 全部静态 import 进 `resources`，约 350 KB 在主 chunk 里，不管界面语言是什么都要解析。C12 清理后降到约 220 KB，仍然可观。

**做法**：`resources` 只内联 `en_US` + `zh_CN` 兜底，其余改成动态 `addResourceBundle`——在 `App.jsx` 的 `appLanguage` effect 里 `await import(\`./locales/${file}.json\`)` 之后再 `changeLanguage`。多语言界面功能完整保留，但只加载实际用的那一种。

> 采纳了可选项②（只留中英）就**不用做这一项**，两种语言直接内联更简单。

### P3 启动路径去串行

**问题**：`src/main.jsx` 是 `initStore().then(async () => { await initEnv(); ...render })`——先等 store 文件读完，再等 4 个 OS 信息 IPC（`type` / `arch` / `version` / `getVersion`）串行返回，才开始渲染。首屏白屏时间 = 两段 IPC 之和。

**做法**：`Promise.all([initStore(), initEnv()])` 并行；`initEnv` 内部那 4 个 await 也并成一个 `Promise.all`。

### P4 修掉 `lang_detect` 每次调用都重建检测器

**问题**：`src-tauri/src/lang_detect.rs` 的 `lang_detect` command 里每次调用都执行一遍 `LanguageDetectorBuilder::from_languages(&languages).build()`，22 个语种的模型每次重新构建。划词翻译每输入一次就走一遍，是实打实的 bug。`init_lang_detect()` 预热出来的 detector 是个局部变量，用完就丢，完全没起到缓存作用。

**做法**：用 `once_cell::sync::Lazy`（项目已依赖 `once_cell`）把 detector 做成全局静态，`init_lang_detect()` 改成触碰一次这个静态量完成预热。

**顺带**：`Cargo.toml` 里 `lingua` 开了 22 个语种的模型 feature，这是二进制体积第一名。砍到 `chinese, japanese, english, korean` 4 个语种能省下相当可观的体积——**需要你确认常用语种范围**。裁剪时 `lang_detect.rs` 里两个 `languages` 数组和 `match lang` 分支要同步改（现有代码本身有小 bug：`init_lang_detect` 的数组含 `Ukrainian`，`lang_detect` 的数组不含，但 `match` 里又有 `Language::Ukrainian` 分支）。

### P5 加 Rust release profile

**问题**：`src-tauri/Cargo.toml` 完全没有 `[profile.release]`，用的是 Cargo 默认（`opt-level = 3`、`lto = false`、`codegen-units = 16`、不 strip）。

```toml
[profile.release]
opt-level = "s"      # 体积优先；若感觉运行变慢改回 3
lto = true
codegen-units = 1
strip = true
```

`panic = "abort"` 能再省一些体积，但会让 panic 直接终止进程而不是 unwind——pot 里有不少 `.unwrap()`，**建议先不加**。代价是 `lto = true` + `codegen-units = 1` 让 release 构建时间大约翻倍。

### P6 收敛 `useConfig` 的事件监听

**问题**：`hooks/useConfig.jsx` 每个 key 都 `listen()` 一个独立的 tauri 事件。`TargetArea` 一个组件里有 10 个 `useConfig`，而 `TargetArea` 按翻译服务数量渲染多份——4 个服务就是 40 个监听器，每个都是一次 IPC 注册。

**做法**：
1. **短期**：把 `TargetArea` 里跨实例相同的配置（`appFontSize`、`autoCopy`、`hideWindow`、`clipboardMonitor`、`translateSecondLanguage`）提到 `Translate/index.jsx` 读一次，用 props 或 jotai atom 往下传。改动小、风险低。
2. **中期**：给 `useConfig` 加模块级注册表，同一个 key 只注册一个 tauri listener，多个组件订阅同一个回调。收益覆盖整个应用，但要小心 `syncToStore` 的 debounce 是 per-hook 实例的，合并时别把不同组件的写入互相 debounce 掉。

### P7 daemon 窗口改懒创建（需实测）

**问题**：`tauri.conf.json:110-118` 在启动时就创建了隐藏的 `daemon` 窗口（`daemon.html`）。它唯一的用途是 `window.rs::get_current_monitor()` 里枚举显示器（Tauri v1 的 `AppHandle` 没有 `available_monitors`，必须借一个 Window）。Windows 上一个 WebView2 实例大概占 30~60 MB，而 pot 大部分时间是驻留托盘不干活。

**做法**：`get_daemon_window()` 里已经写好了「找不到就创建」的兜底分支，所以从 `tauri.conf.json` 的 `windows` 数组里删掉 daemon 配置就变成懒创建。注意这只是把开销**推迟**到第一次划词，之后窗口仍然常驻；要真省内存得用完 `close()`，但那样每次划词都要重建 WebView，可能反而更卡。

**建议**：先只做懒创建，用任务管理器实测「启动后驻留托盘」和「用过一次之后」两个状态的内存，再决定要不要 close。

### P8 tray.rs 去重（可选）

11 个 `tray_menu_xx()` 函数结构完全一样，只有字符串不同，占了 27 KB 里的绝大部分。可以改成一个 `tray_menu(labels: &TrayLabels)` + 一张语言到字面量的表。主要是可维护性收益，编译后体积省得不多。如果采纳可选项②（只留中英），这一项在 C12 里就顺带做完了。

### 明确不做的优化

`clipboard.rs` 的 500 ms 轮询看着刺眼，但循环在 `clipboard_monitor` 为 false 时会 `break` 退出，默认关闭时零开销，不值得改。
